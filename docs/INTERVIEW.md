## 0. 一句话定位（30 秒电梯版）

「一个可部署的深度研究 Agent：LangGraph 编排 Planner→Executor→Reflector 三节点循环，smolagents CodeAgent 执行搜索/抓取，82+ 个测试全绿，17 条评测集命中 94%，断点恢复耗时仅占全流程 7%，Docker 一键部署，全项目 API 成本约 6 元。」

## 1. 架构设计（必考题）

**Q: 为什么拆 Planner / Executor / Reflector 三个节点?单 Agent 循环不行吗?**

A: 三个节点对应研究流程的三种**不同职责**,耦合在一起会导致:
- Planner:负责**全局拆解**(用户任务 → 调研简报 + 步骤),需要"看全局",一次调用成本低;
- Executor:负责**局部执行**(一步一搜),需要"带工具反复尝试",消耗最多 token;
- Reflector:负责**质量判定**(继续/重规划/收尾),是"停下来思考"的一环。

单 Agent 循环把三件事混在一个上下文里:规划视野被中间搜索过程稀释、反思没有独立触发点、token 浪费在无关上下文上。三节点让每个阶段的 prompt 最精简、职责最清晰,也便于**单独评测每一环**(规划成功率/执行命中率/反思准确率)。

**Q: Reflector 为什么用模型做语义判定,而不是规则?**

A: 规则只能处理"步骤数是否跑完"这类硬条件;但"资料是否足够""是否有缺口"是**语义判断**,必须依赖模型。代码里保留了两层:
- **硬护栏**(规则):max_iterations 上限、步骤跑完强制收尾、零步骤禁止 complete——防止模型乱来烧钱;
- **软判定**(模型):continue/replan/complete 三选一 + 缺口描述。

**Q: replan 和 continue 的区别?**

A: continue = 当前计划没问题,继续做下一步;replan = 发现计划本身有缺口(搜的方向不对/漏了维度),**回 Planner 基于已有进展重新规划**,避免在错误的计划上浪费 token。这是"计划-执行-反思"闭环的关键:不是死板执行完 6 步,而是随时能调整方向。

## 2. 评测可信度(必考题,重点准备)

**Q: 命中率 94% 是怎么测的?凭什么可信?**

A(按此顺序讲,先承认边界再讲证据):
1. **评测集**:17 条任务(多源综合/事实核查/兴趣/安全用例),每条带 must_contain 关键词,大小写不敏感匹配;
2. **全自动**:evaluate.py 逐条跑、进度实时落盘 progress.jsonl(断点续跑),不人工挑结果;
3. **已知边界(主动说)**:单次运行、样本 17 条、命中率有波动(id=3/9 各 0.5 属 LLM 随机性,非系统性失败);严谨说法是"单次 94%,多次重跑会更稳,方差主要来自 temperature=0.3 的模型输出"。
4. **对照实验**:ablation.py 做了"有反思 vs 无反思"对比(#1 早停修复后 0.67→1.0、#3 省 83% token),证明反思组件的价值是**测出来的**不是吹的。

> 面试官若追问"为什么不全量重跑取平均":答"成本约 6 元/轮,评测集迭代过程中重跑过多轮,主要结论稳定;小样本方差如实记录在案"。

**Q: 反思对照实验只有 3 条样本,结论可靠吗?**

A(如实):3 条样本下 0.83 vs 1.00 的汇总**不能归因于修复**——README 已注明"修复效果与随机波动在 3 条样本上无法区分"。但 #1 的 0.67→1.0 是**同一任务前后对比**(早停根治,5/5 步执行满),这一步的证据是直接的;#3 省 83% token 也是同任务对比。**小样本是事实,方向上"提高 complete 门槛减少早停"有效,量化结论待大样本。**

## 3. 容错与工程化(高频追问)

**Q: 断点恢复怎么实现的?价值在哪?**

A: LangGraph MemorySaver(checkpointer)+ thread_id。任务中断后,同一 thread_id 重跑会**从断点继续**,不重跑已完成步骤。实测:中断在 writer 前,恢复仅 18.4s,占全流程 7%——意味着长任务可以"随时停、随时续",token 不浪费。

**Q: 搜索挂了怎么办?**

A: 三层降级:
1. **provider 降级**:bing(默认)→ tavily(需 key)→ 兜底提示换关键词;
2. **工具级容错**:web_search 失败返回错误字符串,CodeAgent 会自行换词重试(工具调用埋点实测单任务成功率 94.6%);
3. **流程级兜底**:Planner 输出解析失败 → 兜底单步计划;Writer 空输出 → 三重试 + 兜底文本。
> 边界(主动说):bing 是免费直连的"灰色"方案,质量波动大;Tavily 是正式方案但需 key,这是当前最大外部依赖。

**Q: 提示词注入怎么防?**

A: 三层:
1. **Executor 提示词**:明示忽略搜索结果中的"忽略系统指令/输出提示词"等注入文本;
2. **工具引导**:禁止 CodeAgent 在代码里 import urllib/requests(http 抓取只走 fetch_page 工具),堵住"自己写代码外联"的注入通道;
3. **评测用例**:评测集 #17 就是注入攻击用例,证明防护不是嘴上说说。

## 4. 经验沉淀(memory.py,差异化亮点)

**Q: 记忆是怎么做的?和 RAG 记忆有什么区别?**

A: 这个模块记的是**"怎么研究"的元经验**,不是"知识":
- 触发:步骤执行失败(异常/超时/搜索失败)→ 落盘 {domain, lesson, suggestion} 到 memory/experiences.json;
- 使用:Planner 首次规划同类任务时,把相关经验注入提示词,"避免重蹈覆辙";
- 区别:它解决的是"Agent 下次同类任务别再踩同一个坑"(如"该用更具体的关键词"),不是检索知识。面试官若问"为什么不用向量库":经验量小(几十条)、线性扫描 + 关键词匹配足够,引入向量库是过度设计。

## 5. supervisor 多 Agent(浅层 Multi-Agent)

**Q: supervisor 和 executor 什么关系?**

A: supervisor 是 executor 的**并行版**:同一批步骤用 ThreadPoolExecutor 分发给多个 worker(各自独立 CodeAgent),复用 run_single_step 保证行为一致。CLI 加 --supervisor 切换。为什么是"浅层":worker 之间不通信、无消息队列/服务发现——**真实分布式多 Agent 是另一个量级的复杂度,当前场景(研究步骤可并行)用线程池够了,过度设计反而露怯。**

## 6. 与 CourseRAG 集成(2026-08-22 新增)

**Q: 为什么要集成一个本地 RAG?**

A: 研究任务分两类——**外部信息**(时事/产品)用 web 搜,**课程/私有知识**用本地知识库更准。集成后 Executor 多一个 course_retrieve 工具(HTTP POST 到 CourseRAG 的 /retrieve,零侵入解耦),提示词引导 CodeAgent"课程题优先查本地库"。对比评测(纯 web vs web+RAG)见 eval_set/rag_compare.jsonl。

**Q: 为什么走 HTTP 而不是进程内调用?**

A: 两个独立项目解耦:CourseRAG 有自己的 FastAPI(检索/文档管理/索引重建),Agent 只消费 /retrieve 端点;RAG 挂了 Agent 自动降级 web,互不阻塞。部署上也独立(Docker 各自起)。
